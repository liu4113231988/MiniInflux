# 持续写入测试后的优化计划（2026-09-09）

## 测量范围

本轮只新增压测与汇总脚本，没有修改引擎、WAL、flush 或持久化配置。使用当前 Release 构建、独立临时数据库目录、本机 HTTP、每请求 5,000 点、16 个 series、一个整数 field、唯一时间戳。写入 worker 为闭环：准备下一批数据，然后等待 HTTP ACK。生成数据计入总吞吐耗时，单独记录 PrepareMs，不计入请求延迟。与上一轮浮点等负载不同，不能直接比较历史吞吐数值。

主测试持续 300 秒、4 并发；补充测试持续 120 秒、16 并发。默认 WAL fsync=true、间隔 1000 ms，flush 阈值 50,000 点、buffer 点数上限 1,000,000，MaxBufferBytes=0；诊断开启，每 2 秒采集服务进程内存、CPU 累计时间和 /debug/stats。没有并发查询业务负载。首 30 秒包含启动/JIT，不作为稳定窗口。

数据全部使用唯一 series/timestamp 组合，结束后显式 flush 并查询 count(value) 核对成功点数。该核对不等价于崩溃恢复或逐值完整性验证；最后仍可能有 compaction 在运行，追加 flush 耗时不代表所有后台合并完成。

## 主测试结果与判断

- 300 秒内成功 150,960,000 点，存储 count 相同，失败请求 0；平均 503,024 points/s。
- 请求 p50=20.51 ms、p95=128.99 ms、p99=215.30 ms。
- 30–60 秒窗口吞吐 586,167 points/s、p99=158.10 ms；270–300 秒窗口为 412,333 points/s、p99=249.21 ms。存在随运行时间下降的现象，单轮不足以区分后台争用、GC、温度或本机其他活动。
- 2 秒采样观测到私有内存峰值 5,702.6 MiB、工作集峰值 5,527.5 MiB；随后内存回落，不能据此认定泄漏。
- buffer 峰值 545,000 点，队列峰值 4 请求；未观察到持续累积至上限。末尾显式 flush 后 buffer=0、queue=0，追加 flush=38.93 ms。
- 结束时完成 9 次 compaction run，另有合并正在运行，backlog=1。backlog 按任务数计量，不能衡量实际待合并字节。
- 默认 MemoryBufferBytes=0 是字节跟踪未启用，不是内存占用为零。
- 累计阶段：FlushEncode=205.15 s、WriteLocked=168.89 s、WalAppend=95.66 s、SegmentColumns=87.34 s、BufferAppend=61.21 s、WalEncode=54.28 s、FlushCleanup=25.29 s、WriteLockWait=18.13 s。阶段嵌套且并行，不能相加或当作 CPU 占比；其中 FlushEncode 内仍有尚未单独覆盖的工作。

## 执行顺序与验收

### 0. 先复现并修复后台合并期间的查询计数异常

16 并发、120 秒：HTTP 全部成功，WritePointsTotal=54,990,000，flush 后 buffer=0，但首次 count(value)=54,230,000，少 760,000 点（约 1.38%）。该轮 Valid=false，不能作为有效性能成绩。保留原始数据目录并复制副本重启后，连续三次 count 都为 54,990,000。当前证据支持运行中可见性/查询快照问题，不支持永久数据丢失的结论；没有做逐值校验。

代码调查发现候选竞态：Compactor.FinalizeCompaction 替换 manifest 后立即删除旧段，而 TsdbEngine 有多个读取路径遇到 FileNotFoundException 直接跳过；元数据索引是在 CompactAll 完成后才统一失效。需要通过确定性并发测试确认具体路径，不能仅凭静态阅读指定根因。

实施：构造读取段列表后暂停查询、发布合并结果并删除旧段、再恢复查询的测试；同时覆盖缓存已热和未热的 COUNT/原始查询。根据复现结果选择段版本快照与读引用保留、延迟回收，或在版本变化时重试整个查询；不能通过简单忽略文件缺失得到成功的部分结果。保持 manifest 发布、缓存更新和读侧快照的一致关系。

验收：4/16 并发持续写入、反复 flush/compaction 下 count 和按时间范围校验一致；重启前后结果相同，不重复也不漏读；全量存储/查询测试通过后才继续性能优化。

### 1. 补齐内存、队列和后台合并的观测

证据：内存峰值约 5.6 GiB，但 buffer 未达到上限；现有字节统计默认无效，只有 compaction 任务数，尚无 GC 暂停或阶段分配数据。

实施：区分 active buffer、flush snapshot、排队请求的点数及估算字节；不依赖启用 MaxBufferBytes 才提供监测。增加队列等待/实际合批点数，compaction 输入/输出字节、耗时与待处理字节；采集 .NET 分配速率、GC 堆和暂停。将 flush 中分 shard、列构造、footer 校验和 checkpoint 的时间拆开，关联请求慢窗口。

验收：计数在成功、失败、取消、flush 后准确回落；诊断关闭的对照吞吐回退不超过 3%。同一工作负载至少重复 3 次，稳定阶段和冷启动分开汇总。

### 2. 限制 compaction 解码与输出缓冲的峰值

代码依据：Compactor.MergeColumnsStreaming 在加入整个 group 后才检查 2,000,000 点预算，单个大 group 可以超出预算；MergeBatch 同时持有解码列和合并结果，输出 chunk 还保留多个完整列。这是内存峰值的候选原因，需阶段 1 的分配证据验证。

实施：按实际估算字节约束输入解码与输出缓冲；大 group 分块解码、游标归并、及时写出并释放；为无时间重叠的有序输入评估直接拼接快路径。先做字节预算和分配微基准，再考虑在写入繁忙时调整合并并发/速率。单纯延后合并可能扩大 backlog，不能单独作为成功标准。

验收目标：同样 5 分钟负载的进程私有内存峰值降低至少 30%，稳定阶段 p99 降低至少 15%，吞吐回退不超过 5%，待合并字节不持续增长。覆盖同时间戳覆盖顺序、tombstone、retention、失败重试及输出文件兼容测试。目标是实施门槛，不是已测收益。

### 3. 减少 flush 清理的持锁扫描与索引重建

证据：FlushCleanup 累计 25.29 s，写锁等待 18.13 s。TsdbEngine.FlushSnapshotAsync 扫描仍在使用的整个 buffer，随后重建剩余点的 series 索引；并发追加越多，重建工作可能越大。

实施：先拆分清理扫描和索引重建计时；尝试按冻结批次维护数据与索引生命周期，完成后移除对应批次，避免反复重建活跃部分。保证查询仍能同时读取活跃/冻结数据，WAL replay floor 只在段文件成功发布后推进。

验收目标：cleanup 持锁时间降低至少 30%，稳定阶段 p99 改善，吞吐不回退；测试覆盖乱序、删除与 flush 并发、flush 失败保留数据、checkpoint 和重启恢复。该结构改动排在测量和合并内存控制之后。

### 4. 给请求队列和合批增加点数/字节预算

代码依据：WriteQueue.QueueCapacity 和合批 BatchSize 当前按请求数计算，单请求又允许多点；即使 buffer 有点数上限，已解析且排队的数据也可能较大。本轮闭环只有 4/16 个在途请求，无法验证极端排队安全性。

实施：同时限制排队请求、点数、字节以及单次合批点数/字节；必要时在解析前获取在途预算。保持取消、失败和成功时预算恰好释放一次；明确超载返回和客户端重试行为。

验收：增加 64 并发、大小批次混合和长字符串压力，检查内存上界与超载错误；正常负载吞吐回退不超过 5%。不要以增加单库 worker 数替代预算，单 db/rp 的写锁仍会串行化。

### 5. 再评估 WAL 编码和跨数据库并行

WalEncode 仍有 54.28 s 累计成本，但当前优先处理持续负载退化与内存。前几项完成后，对重复 measurement/tags 编码复用做格式一致性微基准；通过多 db/rp 负载确认队列是否限制扩展，再评估分区 worker。二进制 WAL 和严格 durable ACK 独立设计，避免混入本轮性能比较。

## 复现与证据

```powershell
dotnet build .\MiniInflux\MiniInflux.csproj -c Release --no-restore -nologo
.\scripts\sustained-write.ps1 -Seconds 300 -Concurrency 4
.\scripts\sustained-write.ps1 -Seconds 120 -Concurrency 16
.\scripts\summarize-sustained.ps1 -RunPath <输出目录>
```

压测结束后再运行汇总，避免分析开销与负载竞争。生成数据保留在 .benchmarks 中，不提交。主测试证据目录：`.benchmarks/sustained-a3d2145cbfd243bbbfb7cab92eb9a47c/`，包含 requests.json、telemetry.json、count.json、result.json、summary.json 和服务日志。

16 并发证据目录：`.benchmarks/sustained-99b6fa0ff6d44a84b28f42f075ca83a4/`，额外保留 recheck-data 副本及 recheck-counts.json。该轮观测 ACK 约 457,506 points/s，p95=378.06 ms、p99=620.23 ms；末 30 秒 p99=949.03 ms，队列峰值 16。由于计数校验失败，这些仅用于定位压力现象，不作为性能验收结果。其前约 30 秒与主测试结果汇总有短暂重叠，比较时应排除；30–120 秒各窗口仍未表现出增加并发的吞吐收益。两轮运行时长不同且各只有一轮，不能作严格因果对照。

本轮最初脚本在请求结束后先保存请求 JSON，再执行 flush，因此 38.93/98.16 ms 是该保存间隔之后的 flush 耗时，不能反映停止发压瞬间的积压。现已将请求 JSON 保存移到 flush/count 之后，供后续复现使用；本轮旧结果保持原样，不追溯改写。采样间隔可能漏掉短时峰值，进程内存也不是 GC 堆大小。

## 2026-09-10 审查与正确性补完

本次审查保留批量 LVC、乱序列构造、编码复用、WAL 批位置接口与默认关闭的阶段诊断。完成阶段 0 的 compaction 读一致性修复：引擎读取及 SELECT/流式查询持有可跨线程释放的读取凭据；合并编码仍在读侧并行进行，发布 manifest、清除元数据缓存、删除旧段则等待现有读取完成。原先在整个 CompactAll 返回后清理缓存的操作已移至每次发布内部。

回归测试在流式读取暂停时等待合并输出文件生成，验证旧输入仍存在、合并尚未发布、嵌套 COUNT 不死锁、剩余原始值完整，并校验发布后结果；分别覆盖元数据缓存冷/热。另验证跨线程释放、重复释放与取消。全量 425 项测试通过，Release 解决方案构建通过（已有 StorageHealth/AuthenticationGuard 警告保留）。

代价：长查询或未释放的枚举会延后合并发布；连续重叠的读取也可能延长等待。本机制仅协调 compaction 发布，不提供与并发写入/删除之间的完整事务快照。后续阶段 1–5 仍是优化规划，本批没有实施合并内存预算、flush 数据结构重构或严格 durable ACK。

同时修正 README 中“进程崩溃不会丢已确认写入”的过强保证：当前 ACK 不等待 fsync，FileStream 进程缓冲也存在风险，刷盘代码和策略未改变。持续基准增加连续三次 COUNT 校验，并在不一致时保留结果后报错；请求 JSON 写出放在最终 flush/count 之后。

复测状态：首轮 16 并发/120 秒写入 68,675,000 点，零失败且连续三次 COUNT 一致；第二轮成功 70,780,000 点，三次 COUNT 一致，但有 8 次启动期 429，已作为未通过零拒绝性能校验的结果保留。压测脚本支持 -DiagnosticLog 将警告保存在隔离运行目录，辅助区分限流原因。

第三轮同样 16 并发/120 秒并开启独立警告日志，成功 70,720,000 点、零失败，连续三次 COUNT 一致，未再出现写入拒绝。阶段 0 的本次修复与验证已完成；内存预算、flush 重构和队列预算属于后续性能工作，不作为已经完成的能力。
