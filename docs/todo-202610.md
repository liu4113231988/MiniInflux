## 一、写入路径后续优化

来源：`todo.md` 2026-09 章节中写入优化方案的阶段 2–4 与持续写入计划的阶段 1–5。

### P1 — 观测与背压

- [x] 补齐内存、队列与后台合并的观测：区分 active buffer / flush snapshot / 排队请求的点数与估算字节；compaction 输入/输出字节、耗时与待处理字节；采集 .NET 分配速率、GC 堆与暂停。
- [x] 请求队列与合批增加点数/字节预算：同时限制排队请求、点数、字节与单次合批大小；解析前获取在途预算，失败/取消/成功恰好释放一次，明确超载返回与客户端重试行为。

### P1 — flush 与写入互相阻塞

- [x] 分离 active buffer 与 immutable flushing buffer，锁内交换引用、锁外编码，查询同时读取两代并维持 LWW。
- [x] 每代持有独立 series 索引、计数与 WAL replay floor，flush 成功后整体退休，避免扫描活跃 list 与重建索引。
- [x] 为 flush/compaction 设置有界并发与调度预算；先以 CPU/磁盘证据决定编码或调度改动。

### P2 — compaction 内存峰值

- [x] 按估算字节约束单批解码预算：2026-10-25 审计后将批预算从 200 万点改为 64 MiB 解码字节，峰值直接有界。
- [x] 大 group 分块解码、游标归并、及时写出释放；评估无时间重叠有序输入的直接拼接快路径。

### P2 — 扩展写入并行度

- [x] 经过并发安全审计后按数据库路由到固定数量 worker（同库有序）；修正 `_bufferedPointCount/_bufferedByteCount` 的原子性与上限。
- [x] 审计 schema/manifest/DDL/WAL checkpoint/跨库 flush 与直接 `WriteAsync` 调用；WAL 先允许准备并行、追加有序，再据实测考虑更大的 group commit。

### P3 — 数据模型改造（仅在 CPU/GC 仍占主导时推进）

- [x] 二进制 WAL：新写入使用带版本标识（magic 0x01）的二进制格式，回放同时支持旧文本与新二进制，损坏/截断在安全点停止；体积 59.6–90.2 B/point → 21.6–31.2 B/point（−64~65%），decode 吞吐 1.17M→4.14M pts/s（2t2f）。
- [ ] 将每点 tags/fields 字典改为批内只读 series 描述与紧凑字段数组（compact-row）。
