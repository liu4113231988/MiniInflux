## 一、写入路径后续优化

来源：`todo.md` 2026-09 章节中写入优化方案的阶段 2–4 与持续写入计划的阶段 1–5。

### P1 — 观测与背压

- [ ] 补齐内存、队列与后台合并的观测：区分 active buffer / flush snapshot / 排队请求的点数与估算字节；compaction 输入/输出字节、耗时与待处理字节；采集 .NET 分配速率、GC 堆与暂停。
- [ ] 请求队列与合批增加点数/字节预算：同时限制排队请求、点数、字节与单次合批大小；解析前获取在途预算，失败/取消/成功恰好释放一次，明确超载返回与客户端重试行为。

### P1 — flush 与写入互相阻塞

- [ ] 分离 active buffer 与 immutable flushing buffer，锁内交换引用、锁外编码，查询同时读取两代并维持 LWW。
- [ ] 每代持有独立 series 索引、计数与 WAL replay floor，flush 成功后整体退休，避免扫描活跃 list 与重建索引。
- [ ] 为 flush/compaction 设置有界并发与调度预算；先以 CPU/磁盘证据决定编码或调度改动。

### P2 — compaction 内存峰值

- [ ] 按实际估算字节约束输入解码与输出缓冲；大 group 分块解码、游标归并、及时写出释放；评估无时间重叠有序输入的直接拼接快路径。

### P2 — 扩展写入并行度

- [ ] 经过并发安全审计后按数据库路由到固定数量 worker（同库有序）；修正 `_bufferedPointCount/_bufferedByteCount` 的原子性与上限。
- [ ] 审计 schema/manifest/DDL/WAL checkpoint/跨库 flush 与直接 `WriteAsync` 调用；WAL 先允许准备并行、追加有序，再据实测考虑更大的 group commit。

### P3 — 数据模型改造（仅在 CPU/GC 仍占主导时推进）

- [ ] 将每点 tags/fields 字典改为批内只读 series 描述与紧凑字段数组，评估二进制 WAL（版本标识、旧记录恢复、混合版本回放与损坏检测）。
